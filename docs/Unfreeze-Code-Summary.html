Unfreeze software implementation

Arduino UNO Q · App Lab build freeze-pulse-alarm-v3 · Report text and presentation notes

Report text

Unfreeze is a wearable prototype that uses two on-device Edge Impulse models to decide when to offer a cue. A chest-facing USB camera looks for a doorway ahead. A separate movement model uses three axes of acceleration from a lower-back sensor to classify the current window as freeze or normal. Each model can trigger its own response. A doorway can prompt an audio rhythm while walking remains normal, and a movement event can trigger thigh vibration even when no door is visible.

The UNO Q divides the work between its Linux processor and its microcontroller. Linux runs both models and decides which cue to request. The microcontroller samples the Movement module and times the Vibro and Buzzer outputs. The Android app and web page connect over the phone’s hotspot to configure cues, play a selected soundtrack and inspect live results. Inference runs on the board without an internet connection.

During an active session, the software checks several observations before acting. Two qualifying doorway detections can start an audio rhythm. Two qualifying movement windows can start a five-second vibration. A separate rule checks whether the freeze score has stayed high often enough over five seconds to warrant a five-second alarm. Keeping those decisions separate lets the system give an early cue and reserve the alarm for a persistent pattern.

A timeline for the slide

Set 0.00 s at the first qualifying model result. In an uninterrupted example, the second result at 0.25 s starts Vibro. The first eligible alarm decision is at 5.00 s. The vibration command ends around 5.25 s. The two clocks start at different observations. Actual timing also includes inference and hardware communication.

Sampling continues while the motor runs. Windows that overlap vibration or settling can help evaluate an existing episode. Only clean windows can start a new episode or trigger another vibration. Physical testing is needed to measure how much motor vibration changes the scores.

English speaker notes · about 75 seconds

Imagine walking toward a doorway. Our camera looks for a door near the centre of the image. After two consistent detections, the system can play a rhythm on the phone or use the board’s buzzer. That cue is based on what lies ahead. It can happen even when the person is walking normally.

A second model listens to the movement sensor. It analyses two seconds of acceleration at a time and updates roughly four times a second. When two windows in a row score at least zero point seven for freezing, the board commands five seconds of thigh pulses.

We use a separate clock for the alarm. It starts at the first qualifying score. After five seconds, if at least three quarters of the recent scores still qualify, including the latest one, the buzzer sounds continuously for five seconds. A brief dip is allowed.

Both models run on the UNO Q. On this screen we can follow a decision from the camera box or movement score through to the output command. We have tested that software sequence. Timing the physical cues and evaluating their effect on walking are separate validation steps.

Evidence for questions

What was verified? The UNO Q sketch compiled and 27 board-software tests passed. One deterministic test supplied a temporary dip in the freeze score while a five-second motor command was active and checked the alarm time. The build reported 126,508 bytes of program storage and 57,868 bytes of static RAM for the MCU sketch. These figures exclude the Linux models.

What remains open? At the time this summary was prepared, deployment and physical cue timing for this build had not been confirmed in the project record. The movement model has two labels, freeze and normal. Its lower-back axis mapping still needs a mounting check. Clinical benefit has not been established by these software tests.

How can the team check before presenting? On the hotspot, open the board’s build page and look for appBuild = freeze-pulse-alarm-v3 and mcuCueRevision = 3 with mcuFreezeHoldMs = 5000.
